# Static sprite manifest pipeline — design (Sprites epic, Slice 1)

**Date:** 2026-07-25
**Status:** Design, pending implementation plan
**Related skills:** [sprite-pipeline], [local-ai-dev], [js-game-dev]

## Epic context

The full ask (directional + animated action sets for many heroes/creatures, a
hero picker) is an **epic**, decomposed into slices because the pieces have very
different feasibility. The animation-*generation* piece carries a real CPU
consistency/quality risk and must not block the feasible pieces.

| Slice | Deliverable | Feasibility | Depends on |
|-------|-------------|-------------|------------|
| **1 (this doc)** | Manifest + runner + static directional idle sprites | High | existing SD service |
| **2** | Client action dimension — `action/dir/frame` atlas keys, render-mode by gameplay state | High (data+client) | Slice 1 |
| **3** | Hero-selection UI — model hero skins + in-game picker | High (frontend) | Slice 1 (hero atlases) |
| **4** | Action-animation generation — pose skeletons + action frame sets | Risky (CPU consistency; needs frame-source decision) | Slices 1–2 |

Each slice ships something usable and gets its own spec → plan → build. This
document specs **Slice 1** only.

## Problem

The game needs sprites for many actors (10+ selectable heroes; creatures: wolf,
slime, skeleton, bat, zombie, leech, village guard, boar, rabbit, gargoyle, fox,
hornet) and scenery (tree, bush, icerock, stone, boulder). The original ask was
for full action animation — 8 movement directions plus attack/magic/ranged/
crouch/damage/jump/use-item, each 7–10 frames, per entity.

That ask is not feasible with the available tooling, for two independent reasons:

1. **No usable image generator except the local SD container.** The only image
   generators the developer can drive are the local Stable Diffusion container
   (`sprite-gen/`) and — indirectly — nothing else. Claude CLI and the
   Antigravity agent are *coding/reasoning* agents; they do not emit image
   pixels. There is no cloud image API key in play.
2. **Consistency, not speed, is the real wall.** Smooth N-frame animation of a
   *consistent character* across 8 facings and 8 actions is a research-grade
   problem. The local SD pipeline achieves frame consistency only via fixed
   seed + ControlNet pose skeletons, and even then only for a single hardcoded
   walk cycle. Independent text2img cannot hold a character stable across
   hundreds of frames.

## Decision

**Scope down to static, directional idle sprites, generated by the existing
local SD service, driven by a committed JSON manifest and a re-runnable
command.** This is the tractable slice of the original vision and delivers the
concrete artifacts the developer asked for (a JSON description file + a rerun
command).

- **Static only.** One idle frame per facing. No animation, no action dimension.
- **8 facings for actors** (heroes + creatures) so they face their movement
  direction. **Flat single frame for scenery.**
- **Generate-only.** The runner produces + stores atlases and reports; the
  developer approves chosen atlases via the existing admin UI. No DB writes in
  the runner.

### Cost envelope

| Group    | Count | Facings × frames | Frames |
|----------|-------|------------------|--------|
| Heroes   | ~10   | 8 × 1            | ~80    |
| Creatures| ~12   | 8 × 1            | ~96    |
| Scenery  | ~5    | 1 × 1            | ~5     |
| **Total**|       |                  | **~181** |

At ~60–70s/frame on CPU (`sd-turbo`) ≈ **~3 hours** of background compute — a
run-overnight job. Contrast the original animated matrix (~6,400+ frames,
~5 days) which is why that was rejected.

## Architecture

A single new command layered on the **existing** infrastructure — no changes to
the SD service's generation core, no client changes expected.

```
sprites.manifest.json ─► gen-sprites runner ─► backend admin API ─► sprite-gen ─► MinIO
  (committed)             (Node CLI)            /api/sprite-jobs     (existing)   (existing
                             │                  /api/entity-jobs                   keys)
                             │                  (existing, unchanged)
   sprites.manifest.lock ◄──┤ (fingerprints)
   (committed)              ▼
                     run report (stdout) + per-entity approve hint
```

**Why through the backend admin API, not sprite-gen directly:** the approve
endpoint (`POST /api/entity-types/:id/sprite`) updates a `sprite_sets` row keyed
by `job_id`, and that row is created only by the backend's `/api/sprite-jobs` /
`/api/entity-jobs` routes — never by a direct sprite-gen call. Driving the admin
API is therefore what keeps "approve via the existing UI" working with **zero**
backend/UI changes. The cost is that the runner authenticates as admin
(`POST /api/auth/login`).

### 1. Manifest — `sprites.manifest.json` (repo root or `sprite-gen/`)

```json
{
  "version": 1,
  "defaults": { "backend": "sd-turbo", "size": [128, 160], "seed": 0 },
  "entities": [
    { "name": "Wolf",        "kind": "creature", "seed": 101,
      "prompt": "a grey forest wolf, isometric game sprite, transparent background" },
    { "name": "hero_knight", "kind": "creature", "seed": 201,
      "prompt": "a human knight in plate armour with a sword, isometric" },
    { "name": "Tree",        "kind": "object",   "seed": 301,
      "prompt": "a tall broadleaf tree with a thick trunk" }
  ]
}
```

- `name` — subject key; also the MinIO folder (`sprites/<name>/…`).
- `kind` — `creature` → 8 facings × 1 idle frame; `object` → 1 flat frame.
- `prompt` — the per-entity render description (the "prompt field" from the ask).
- `seed` — locks reproducibility; distinct per entity.
- `defaults` — merged into each entity; per-entity fields override.

The committed manifest ships with the full roster: 10 hero archetypes
(knight, mage, ranger, rogue, paladin, barbarian, cleric, druid, warlock, monk —
prompts are starting points to edit), the 12 named creatures, and the 5 scenery
objects. Wolf/Slime/Skeleton/Bat/Tree/Stone/IceRock reuse the prompts already in
`backend/migrations/1714440033000_entity_prompts.js`.

### 2. Runner — Node CLI

`npm run sprites:gen -- [--only nameA,nameB] [--force] [--manifest path]`

Setup: the runner logs in (`POST /api/auth/login`, admin creds from env) once to
get a bearer token, and fetches `GET /api/entity-types` to map entity `name` →
`id` for approve hints.

Behavior per entity:
1. Merge `defaults` + entity fields. `creature` → `frames: 1`, all 8 facings via
   the backend's `/api/sprite-jobs` (directional) path; `object` → flat single
   frame via `/api/entity-jobs`.
2. Compute a **fingerprint** = hash(`kind|prompt|seed|size`). If the committed
   lockfile `sprites.manifest.lock.json` has a matching fingerprint for this
   `name` and `--force` is absent, skip (idempotent rerun). Otherwise POST the
   job, poll the matching `/api/{sprite,entity}-jobs/:jobId` until `done`/`error`.
3. On success the sprite-gen service has already written
   `sprites/<name>/atlas.{png,json}` + per-frame PNGs to MinIO, and the job
   `result` carries `{atlas_key, manifest_key, frame_keys}`. Runner updates the
   lockfile entry for `name` with the new fingerprint + `atlas_key`/`job_id`.
4. Emit a run report: per-entity status (generated / skipped / failed), the
   atlas key, and — where the entity `name` matches an `entity_types` row — the
   exact approve call (`POST /api/entity-types/:id/sprite` with
   `{atlas_key, manifest_key, job_id, animated: true, frames: 1}`) so the
   developer can approve straight from the report. Heroes (no matching row) are
   listed as generated-only, awaiting the hero-chooser follow-up (Slice 3).

The runner reuses global `fetch` (Node 18+, as the existing bridge does); it
needs no MinIO or DB client. Approval stays a deliberate manual step.

### 3. Directional static rendering — expected zero client change

RenderSystem's animated path (`animatedFrameKey(manifest, dir, timeMs, fps)`)
cycles `<dir>/*`. With exactly **one** frame per direction it always resolves
`<dir>/0` — i.e. directional but motionless. So approving these atlases with the
**animated/directional render_mode** yields directional idle for free. The
static render_mode (`staticFrameKey` → `S/0`) ignores facing and is *not* what we
want for actors.

**Verify in the plan:** confirm the 1-frame animated path renders directional
idle with no flicker. Fallback if not: a small `directional-static` mode in
`spriteAtlas.js` / `RenderSystem.js` that picks `<facingDir>/0` without cycling.

## Testing

- **Runner unit tests:** manifest parse + defaults merge; fingerprint stability;
  `--only` / `--force` selection; skip-on-unchanged; report shape. Mock the HTTP
  service.
- **Service smoke:** one `creature` and one `object` entity through the real
  `stub` backend (instant, no ML) end-to-end into a local MinIO, asserting the
  expected atlas keys and 8 directional frames exist.
- **Render check:** manual browser verification (per [browser-verification-lessons])
  that an approved directional-idle actor faces its movement direction.

## Scope boundaries

**In:** manifest schema; Node runner with idempotent rerun + report;
full-roster manifest content; generate + store to MinIO; docs/skill note.

**Out of Slice 1 (owned by later slices, not dropped):**
- Client `action/dir/frame` support → **Slice 2**.
- Animation / action-set generation (attack/magic/ranged/crouch/damage/jump/
  use-item) → **Slice 4** (carries the CPU consistency/frame-source risk).
- Hero-selection UI / "player picks a hero" → **Slice 3**; Slice 1 only
  produces + stores the hero atlases.

**Out of the epic entirely:**
- Auto-registration onto `entity_types` (runner is generate-only, by choice).
- Any new cloud image backend.

## Risks & open questions

- **Static idle quality on `sd-turbo` (no ControlNet on CPU).** The CPU recipe is
  poseless text2img; directional consistency across the 8 facings of one actor
  may be weak. Mitigation: fixed per-entity seed; accept that static idle has a
  much lower consistency bar than animation. Revisit backend/recipe if quality
  is unacceptable.
- **Approving runner-generated atlases — resolved.** Because the runner drives
  `/api/sprite-jobs` / `/api/entity-jobs`, each generation creates the
  `sprite_sets` row the approve endpoint keys on, so the existing approve path
  works unchanged. The report prints the exact `POST /api/entity-types/:id/sprite`
  payload. (An "approve from the report/UI without pasting" affordance stays an
  optional QoL follow-up.)
- **Heroes have no `entity_types` rows.** Generate-only sidesteps this now; the
  hero-chooser follow-up will decide how hero skins are modeled.

## Follow-ups

- **Slices 2–4** per the epic roadmap above (client action dimension, hero
  picker, action-animation generation). Each gets its own spec.
- **"Approve existing atlas" admin affordance** — small quality-of-life fix so
  runner-generated atlases can be approved without re-generating in the UI.
